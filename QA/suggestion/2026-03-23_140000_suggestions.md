## P0-1: Fix Admin Seed Password Complexity Validation

**Resolves:** IMS-BE-SEC-001  
**Effort:** S (Small)  
**File:** `backend/app/main.py` — `_seed_admin_if_needed()` function

**What to do:**
1. Import the password complexity validation logic (or extract it to a shared utility)
2. After the length check, run the same uppercase/lowercase/digit/special checks used in `UserCreate.validate_password_complexity`
3. If the password fails complexity requirements, log an error and skip seeding

**Implementation approach:**
```python
# Extract shared validator to backend/app/utils/validators.py or a new file
def validate_password_complexity(password: str) -> list[str]:
    errors = []
    if not any(c.isupper() for c in password):
        errors.append("one uppercase letter")
    if not any(c.islower() for c in password):
        errors.append("one lowercase letter")
    if not any(c.isdigit() for c in password):
        errors.append("one digit")
    if not any(c in "!@#$%^&*()-_=+[]{}|;:',.<>?/`~" for c in password):
        errors.append("one special character")
    return errors

# In _seed_admin_if_needed():
complexity_errors = validate_password_complexity(admin_password)
if complexity_errors:
    logger.error("ADMIN_PASSWORD does not meet complexity requirements: %s", ", ".join(complexity_errors))
    return
```

**Also resolves:** IMS-BE-DUP-001 (if you extract the shared validator and use it in `UserCreate` and `PasswordChange` models too).

## P0-2: Fix Account Lockout Timing Gap

**Resolves:** IMS-BE-SEC-002  
**Effort:** S (Small)  
**File:** `backend/app/services/user_service.py` — `increment_failed_attempts()`

**What to do:**
1. After setting `locked_until`, the current request should also be aware that lockout has occurred
2. Return the lockout status along with the attempt count so the caller can provide the "Account locked" message immediately on the 10th attempt rather than the generic "Invalid email or password"

**Implementation approach:**
```python
async def increment_failed_attempts(db: Any, user_id: ObjectId) -> tuple[int, bool]:
    """Returns (attempt_count, is_now_locked)."""
    result = await db.users.find_one_and_update(
        {"_id": user_id},
        {"$inc": {"failed_login_attempts": 1}},
        return_document=True,
    )
    if result is None:
        return 0, False

    attempts = result["failed_login_attempts"]
    locked = False
    if attempts >= 10:
        await db.users.update_one(
            {"_id": user_id},
            {"$set": {"locked_until": datetime.now(timezone.utc) + timedelta(minutes=15)}},
        )
        locked = True
    return attempts, locked
```

Then in the login handler, update the caller to use the `locked` boolean — but still show the generic error message (don't reveal lockout to attackers).

**Dependencies:** None.

## P0-3: Handle Auth Token Lifecycle on Page Refresh Robustly

**Resolves:** IMS-CMS-SEC-001, IMS-CMS-SEC-003  
**Effort:** M (Medium)  
**File:** `cms/src/auth/AuthProvider.tsx`

**What to do:**
1. Add a state flag (e.g., `isInitialized`) that prevents child components from making API calls until the initial refresh attempt completes
2. In `tryRefresh()`, only set the token AND user together atomically — if either step fails, set both to null
3. Wire the Axios interceptor to queue requests while `isInitialized` is still `false`

**Implementation approach:**
```typescript
async function tryRefresh() {
    try {
        const resp = await refreshTokenApi();
        if (cancelled) return;
        
        // Fetch user FIRST, only set token if both succeed
        const tempToken = resp.access_token;
        setAccessToken(tempToken);  // Need token to call /me
        
        const me = await fetchMe();
        if (cancelled) return;
        
        // Both succeeded — commit state
        setUser(me);
    } catch {
        if (cancelled) return;
        // Atomic rollback
        setAccessToken(null);
        setUser(null);
    } finally {
        if (!cancelled) setIsLoading(false);
    }
}
```

The key improvement is that `isLoading = true` already prevents child components from rendering (via `ProtectedRoute`). Ensure all API-calling components are behind `ProtectedRoute` and don't fire requests while loading.

**Dependencies:** None.

## P1-6: Fix 401 Queued Request Hanging

**Resolves:** IMS-CMS-SEC-004  
**Effort:** S (Small)  
**File:** `cms/src/api/client.ts`

**What to do:**
In the refresh failure catch block, reject all queued subscribers instead of silently clearing them:

```typescript
} catch (refreshError) {
    // Reject all queued requests
    refreshSubscribers.forEach((cb) => {
        // We need to change the subscriber type to include reject
    });
    refreshSubscribers = [];
    _setAccessToken(null);
    window.location.href = '/login';
    return Promise.reject(error);
}
```

**Better approach:** Change the subscriber pattern to include both resolve and reject callbacks:

```typescript
let refreshSubscribers: Array<{
    resolve: (token: string) => void;
    reject: (err: unknown) => void;
}> = [];

// On success:
refreshSubscribers.forEach(({ resolve }) => resolve(newToken));

// On failure:
refreshSubscribers.forEach(({ reject }) => reject(refreshError));
```
