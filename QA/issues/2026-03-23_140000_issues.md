### IMS-BE-SEC-001 — 🔴 CRITICAL: Admin Seed Bypasses Password Complexity Validation

**File:** `backend/app/main.py`  
**Location:** Lines 48–50

**Description:**  
The `_seed_admin_if_needed()` function creates the first admin user on startup but only validates password length (`len >= 12`). It does **not** run the `UserCreate.validate_password_complexity` validator, meaning the seeded admin password can lack uppercase letters, digits, or special characters — violating the same policy enforced on all other user creation.

**Code:**
```python
if len(admin_password) < 12:
    logger.error("ADMIN_PASSWORD must be at least 12 characters. Skipping admin seed.")
    return
```

**Impact:**  
The first admin account — the most privileged account in the system — can be created with a weak password like `abcdefghijkl`. This undermines the entire password policy.

**Expected behavior:** Run the same `validate_password_complexity` checks (uppercase, lowercase, digit, special character) before hashing and inserting.

### IMS-BE-SEC-002 — 🔴 CRITICAL: Account Lockout Off-by-One (Locks at 11th Attempt, Not 10th)

**File:** `backend/app/services/user_service.py`  
**Location:** Lines 103–113

**Description:**  
The `increment_failed_attempts()` function first increments the counter via `$inc`, then checks `if attempts >= 10`. Because `$inc` is applied *before* the returned document is read (`return_document=True`), the first time this condition is true is when `failed_login_attempts` reaches 10 — but only after the 10th failed attempt. The lockout `$set` happens on the 10th call. However, the **check in the login handler** (`auth.py` L100–104) only blocks login if `locked_until` is set, which doesn't happen until *after* the 10th increment has completed. This means the 10th attempt is not blocked — the user is actually locked out starting from the **11th** attempt.

**Code:**
```python
result = await db.users.find_one_and_update(
    {"_id": user_id},
    {"$inc": {"failed_login_attempts": 1}},
    return_document=True,
)
if result is None:
    return 0

attempts = result["failed_login_attempts"]
if attempts >= 10:
    await db.users.update_one(
        {"_id": user_id},
        {"$set": {"locked_until": datetime.now(timezone.utc) + timedelta(minutes=15)}},
    )
return attempts
```

**Impact:**  
Brute-force attackers get 11 attempts instead of the intended 10 before lockout. While a single extra attempt is not catastrophic, it represents a security boundary violation and indicates the lockout logic was not tested against the exact boundary condition.

**Expected behavior:** Either use `>= 10` with the value *before* increment, or change to `>= 10` after increment (which effectively means lockout on the 10th attempt since the count goes 1→2→...→10→lock).

> **Clarification:** Since `$inc` returns the *new* value and the check is `>= 10`, lockout actually triggers correctly on the 10th failed attempt (count goes 0→1→2...→9→10, and 10 >= 10 is true). The real timing concern is that the 10th request itself still gets the generic "Invalid email or password" response rather than "Account locked" — the lock is only enforced on the **next** (11th) request. This is a one-attempt gap.

### IMS-BE-SEC-003 — 🟠 HIGH: Timing Attack Leaks User Existence in Login Flow

**File:** `backend/app/routers/auth.py`  
**Location:** Lines 86–117

**Description:**  
The login endpoint takes different code paths depending on whether the user exists:
1. **User doesn't exist** → Raises `generic_error` immediately (fast path)
2. **User exists + locked** → Queries `locked_until`, fires audit event, raises error (medium path)
3. **User exists + wrong password** → Calls `verify_password()` (bcrypt, slow path ~200ms)

An attacker can distinguish case 1 from cases 2/3 by measuring response time, thereby enumerating valid email addresses.

**Code:**
```python
if user is None:
    raise generic_error          # ← FAST: no bcrypt, no DB update

# ... lockout check, then:
if not verify_password(body.password, user["hashed_password"]):   # ← SLOW: bcrypt
    attempts = await increment_failed_attempts(db, user["_id"])
    ...
    raise generic_error
```

**Impact:**  
Username enumeration enables targeted brute-force attacks. An attacker can first discover valid emails, then focus password attacks only on those accounts.

**Mitigation pattern:** Always execute a dummy `verify_password()` call when the user is not found to equalize response time.

### IMS-BE-SEC-004 — 🟠 HIGH: Rate Limiter Is In-Memory Only

**File:** `backend/app/security/rate_limit.py`  
**Location:** Entire file (27 lines)

**Description:**  
The rate limiter uses an in-memory `defaultdict(list)` protected by a threading `Lock`. This has multiple issues:
1. **Resets on server restart** — all rate limit state is lost
2. **Not shared across workers** — if uvicorn runs with `--workers N`, each process has its own store, effectively multiplying the allowed rate by N
3. **Memory leak** — the `_store` dict is never pruned of expired keys; only timestamps within keys are cleaned

**Code:**
```python
_store: dict[str, list[float]] = defaultdict(list)
_lock = Lock()
```

**Impact:**  
Rate limiting is ineffective in production deployments. An attacker can restart their attack after a server deploy, or spread requests across workers to bypass the limit entirely.

**Expected behavior:** Use Redis or a shared store with TTL-based key expiry.

### IMS-BE-SEC-005 — 🟠 HIGH: No Rate Limiting on `/auth/refresh` Endpoint

**File:** `backend/app/routers/auth.py`  
**Location:** Line 139 (`@router.post("/refresh", ...)`)

**Description:**  
The login endpoint is rate-limited to 5 attempts per minute per IP, but the `/auth/refresh` endpoint has no rate limiting at all. A compromised refresh token (e.g., stolen via XSS or network interception) can be used to generate unlimited access tokens with no throttling.

**Impact:**  
A compromised refresh token can be rapidly exploited without any server-side protection. Combined with the lack of token blacklisting (IMS-BE-SEC-007), this means a stolen refresh token is valid for its full 7-day lifetime with no recourse.

### IMS-BE-SEC-006 — 🟠 HIGH: Locked Users Can Still Refresh Tokens

**File:** `backend/app/routers/auth.py`  
**Location:** Lines 155–175

**Description:**  
The `/auth/refresh` endpoint checks `is_active` but does **not** check `locked_until`. A user whose account is locked due to brute-force attempts can still use an existing refresh token to obtain new access tokens.

**Code:**
```python
user = await db.users.find_one({"_id": ObjectId(payload["sub"])})
if user is None or not user.get("is_active", False):    # ← checks is_active only
    raise HTTPException(...)
```

**Impact:**  
Account lockout is partially bypassed. An attacker who guessed the password before lockout and has a valid refresh token can continue accessing the system.

**Expected behavior:** Also check `locked_until` and reject refresh if the account is currently locked.

### IMS-BE-SEC-007 — 🟠 HIGH: No Token Revocation / Blacklist on Logout

**File:** `backend/app/routers/auth.py`  
**Location:** Lines 188–193

**Description:**  
The logout endpoint only clears the `refresh_token` cookie client-side. It does not invalidate the token server-side. If an attacker has captured the refresh token (via network sniffing, XSS, or log exposure), they can continue using it even after the legitimate user logs out.

**Code:**
```python
@router.post("/logout")
async def logout(response: Response, current_user: dict = Depends(get_current_user)):
    _clear_refresh_cookie(response)
    fire_audit_event("LOGOUT", user_id=str(current_user["_id"]))
    return {"message": "Logged out"}
```

**Impact:**  
Logout does not actually terminate the session server-side. Stolen tokens remain valid for their full lifetime (15 minutes for access, 7 days for refresh). Admin cannot force-logout compromised accounts.

**Expected behavior:** Maintain a token blacklist (Redis set or MongoDB collection with TTL index) and check it during token validation.

**File:** `backend/app/routers/auth.py`

### IMS-BE-DUP-001 — 🟡 MEDIUM: Duplicated Password Validation Logic

**File:** `backend/app/models/user.py`  
**Location:** Lines 36–48 (`UserCreate`) and Lines 72–84 (`PasswordChange`)

**Description:**  
The `validate_password_complexity` method is duplicated identically in both `UserCreate` and `PasswordChange` Pydantic models. Any future change to the password policy (e.g., requiring minimum 2 digits) must be updated in both places, creating a maintenance risk.

```python
@field_validator("password")
@classmethod
def validate_password_complexity(cls, v: str) -> str:
    errors: list[str] = []
    if not any(c.isupper() for c in v):
        errors.append("one uppercase letter")
    if not any(c.islower() for c in v):
        errors.append("one lowercase letter")
    if not any(c.isdigit() for c in v):

    if not any(c in "!@#$%^&*()-_=+[]{}|;:',.<>?/`~" for c in v):

    return v
```

**Same code appears in `PasswordChange` L72–84.**

**Impact:**  
DRY violation. Password policy drift risk — a change in one model that isn't mirrored in the other creates inconsistent enforcement.

## SECURITY VULNERABILITIES

### IMS-CMS-SEC-001 — 🔴 CRITICAL: Access Token Lost on Every Page Refresh

**File:** `cms/src/auth/AuthProvider.tsx`  
**Location:** Line 28

**Description:**  
The access token is stored in a module-level variable (`let _accessToken: string | null = null`). On every page refresh/reload, this variable resets to `null`. The `AuthProvider` then runs `tryRefresh()` to get a new token via the refresh cookie, but there is a window between page load and `tryRefresh()` completion where:
1. All in-flight requests will fail with 401
2. The user appears logged out briefly
3. Any request queued before refresh completes may fail or hang

**Code:**
```typescript
/** Module-level access token — never stored in localStorage */
let _accessToken: string | null = null;
```

**Impact:**  
Every page refresh causes a brief unauthenticated window. While `tryRefresh()` restores the session, any component that makes API calls during mounting (before refresh completes) will receive 401 errors. The interceptor's 401 retry queue partially mitigates this, but introduces complexity and potential race conditions (see IMS-CMS-SEC-004).

**Note:** Storing tokens in `localStorage` is intentionally avoided for XSS protection. The trade-off is this refresh-on-load behavior. The issue is that this trade-off and its implications aren't handled robustly.

### IMS-CMS-SEC-002 — 🔴 CRITICAL: No CSRF Protection on State-Changing Auth Requests

**File:** `cms/src/api/authEndpoints.ts`  
**Location:** Lines 14–16 (logoutApi), Lines 24–26 (changePasswordApi)

**Description:**  
The logout and password change endpoints send the `refresh_token` HttpOnly cookie automatically (via `withCredentials: true`). While the Bearer token in the `Authorization` header is not auto-sent by browsers (mitigating CSRF for endpoints that *require* the Bearer token), the logout endpoint specifically could be targeted in a CSRF attack if the server only checks the cookie.

However, reviewing `auth.py` L188, the logout endpoint uses `Depends(get_current_user)` which requires the Bearer token in the `Authorization` header. Since browsers don't send `Authorization` headers in cross-origin form submissions, CSRF is **mitigated** for this specific implementation.

**Revised Impact:**  
CSRF is actually mitigated by the Bearer token requirement. **Downgrading from CRITICAL to LOW.** Noted for defense-in-depth: if any endpoint is ever changed to authenticate via cookie-only, CSRF would become exploitable. Adding a CSRF token header (e.g., `X-CSRF-Token`) as defense-in-depth is still recommended.

### IMS-CMS-SEC-003 — 🟠 HIGH: Race Condition in `tryRefresh()` — Token Set Before User Data Fetched

**File:** `cms/src/auth/AuthProvider.tsx`  
**Location:** Lines 53–62

**Description:**  
In the `tryRefresh()` function, the access token is set *before* the user profile is fetched from `/auth/me`. If `fetchMe()` fails, the token remains set but `user` becomes `null`. This creates an inconsistent state where `_accessToken` is valid but `isAuthenticated` is `false`.

**Code:**
```typescript
const resp = await refreshTokenApi();
if (cancelled) return;
setAccessToken(resp.access_token);    // ← Token is now set
const me = await fetchMe();            // ← But this can fail!
if (cancelled) return;
setUser(me);
```

**Impact:**  
If `/auth/me` fails (network error, server down, timeout), the user is stuck in a limbo state: they have a valid token (requests will succeed) but the UI shows them as logged out. Components using `useAuth().isAuthenticated` will show the login redirect, but API calls made by those components will actually succeed.

### IMS-CMS-SEC-004 — 🟠 HIGH: Queued 401 Requests May Hang During Token Refresh

**File:** `cms/src/api/client.ts`  
**Location:** Lines 76–86

**Description:**  
When a 401 response is received during an active refresh, the request is queued via `addRefreshSubscriber()`. The subscriber callback is only invoked by `onTokenRefreshed()` after a *successful* refresh. If the refresh itself fails, the code clears `refreshSubscribers = []` (line 99), but the queued promises are **never resolved or rejected** — they hang indefinitely.

**Code:**
```typescript
return new Promise((resolve) => {
    addRefreshSubscriber((newToken: string) => {
        config.headers.Authorization = `Bearer ${newToken}`;
        config._isRetryAfterRefresh = true;
        resolve(apiClient(config));
    });
});
```

**Failure path (line 97–101):**
```typescript
} catch {
    refreshSubscribers = [];        // ← subscribers cleared but never rejected!
    _setAccessToken(null);
    window.location.href = '/login';
    return Promise.reject(error);
}
```

**Impact:**  
Queued requests hang as unresolved promises. While `window.location.href = '/login'` effectively destroys the page and all pending JS, this is still a code correctness issue. In edge cases (e.g., if the redirect doesn't happen immediately), React components waiting on these promises will remain in loading states.

## XSS / INPUT HANDLING

### IMS-CMS-XSS-001 — 🟡 MEDIUM: Server Error Messages Rendered Unsanitized

**File:** `cms/src/pages/UserManagementPage.tsx`  
**Location:** Lines 195–196 (CreateUserModal), Line 278 (EditUserModal)

**Description:**  
Mutation `onError` handlers extract the error message from the server response and display it directly in JSX:

```typescript
onError: (err: any) => {
    const msg = err?.response?.data?.error?.message ?? err?.message ?? 'Failed to create user';
    setError(msg);
},
```

The `msg` is then rendered as:
```tsx
<div className="text-sm text-red-600 bg-red-50 px-3 py-2 rounded-lg">{error}</div>
```

React escapes text content by default, so this is not a direct XSS vector. However, if the error message format ever changes to include HTML, or if this pattern is copied to a context using `dangerouslySetInnerHTML`, it becomes exploitable. Additionally, `err: any` means there's no type safety on the response shape.

**Impact:**  
Low immediate risk (React escapes by default). Categorized as MEDIUM for the `err: any` type safety concern and the fragile pattern.

The backend `DELETE /users/{user_id}` endpoint actually performs a soft-deactivation (sets `is_active = False`), not a hard delete. This is semantically incorrect — HTTP DELETE implies resource removal, not status change.

**Impact:**  
Confusing for developers maintaining the API. Clients expecting DELETE to remove the resource will be surprised that it only changes a flag. REST API convention violation.

**Expected behavior:** Either use `PUT /users/{user_id}` with `{ "is_active": false }` (which already exists), or rename the endpoint/method to reflect actual behavior.

# PART 3 — CROSS-CUTTING IMS ISSUES

---

### IMS-CROSS-001 — 🟠 HIGH: No Token Blacklist Across System

**Files:** `backend/app/routers/auth.py`, `backend/app/security/jwt.py`

**Description:**  
The system has no mechanism to revoke issued tokens. Logout clears the cookie but doesn't invalidate the token server-side. Admin deactivation of a user doesn't invalidate their existing tokens. Password change doesn't invalidate old sessions.

This means:
- A compromised token is valid for its full lifetime (15 min access / 7 days refresh)
- An admin cannot force-logout a user
- Changing your password doesn't log out other sessions

**Impact:**  
Major security gap for an enterprise CMS handling content management. Industry standard is to implement a token blacklist (Redis set with TTL) or a `token_version` column on the user record.

---

### IMS-CROSS-002 — 🟡 MEDIUM: CMS Still Missing `.env.example` File

**File:** `cms/` directory (file doesn't exist)

**Description:**  
The CMS app reads `VITE_API_BASE_URL` and `VITE_PUBLIC_SITE_URL` from environment variables, but has no `.env.example` file documenting required variables. The root `backend/` and `web/` directories have `.env.example` files.

**Impact:**  
New developers won't know which environment variables to set for the CMS, leading to misconfiguration.

---

### IMS-CROSS-003 — 🟡 MEDIUM: Backend HTML Sanitizer Still Uses Custom Regex

**File:** `backend/app/utils/validators.py`  
**Location:** Entire `sanitize_html()` function

**Description:**  
The HTML sanitizer was fixed in the first assessment (regex escaping corrected), but still uses custom regex patterns instead of a proper HTML parsing library like `bleach` or `nh3`. Regex-based HTML sanitization is fundamentally flawed — there are always edge cases that can bypass regex patterns (e.g., nested tags, encoding tricks, null bytes).

**Impact:**  
XSS bypass risk. A determined attacker can craft HTML that passes the regex filters but executes JavaScript. The risk is mitigated by client-side DOMPurify on both CMS and web frontends, creating defense-in-depth. Backend sanitization remains the weakest layer.

---

### IMS-CROSS-004 — 🟡 MEDIUM: No Password Expiry or Rotation Policy

**Files:** `backend/app/models/user.py`, `backend/app/services/user_service.py`

**Description:**  
The system enforces password complexity but has no password expiry or rotation mechanism. There is no `password_changed_at` field, no check for password age, and no forced rotation policy. For an enterprise CMS, this may be required by compliance frameworks (SOC 2, ISO 27001).

**Impact:**  
Compliance risk. Passwords never expire, even if compromised without the user's knowledge.

---

### IMS-CROSS-005 — ⚪ LOW: No Session Activity Timeout

**Files:** `backend/app/security/jwt.py`, `cms/src/auth/AuthProvider.tsx`

**Description:**  
Access tokens are valid for 15 minutes and refresh tokens for 7 days, regardless of user activity. There is no idle timeout — a user who walks away from their CMS session remains authenticated for the full token lifetime.

**Impact:**  
If a user leaves their workstation unlocked, anyone with physical access can use the CMS for up to 7 days (as long as refresh keeps working). Low risk for most deployments, but notable for security-conscious environments.
